# infra

## What it does
AWS CDK app (Python) that creates every AWS resource Burn uses, in `us-east-1`.
One stack per component, so each owner deploys their part without touching the rest.

## How it works
- `app.py` lists the stacks. Each stack lives in `burn_infra/<name>.py` and can be deployed alone.
- Stacks reference each other by fixed names (`contracts/python/burn_contracts/names.py`), not
  CloudFormation exports, so any stack can be redeployed alone.
- Lambda code is plain Python (stdlib + boto3). `burn_infra/assets.py` copies a handler folder plus the
  shared `burn_contracts` / `burn_detect` packages into `infra/.build/<name>/` at synth time. No Docker.
- System secrets (fingerprint HMAC key, demo token) are generated by Secrets Manager at deploy time.

## How to test it
```bash
cd infra
uv sync
npx aws-cdk@2 synth            # every stack synthesizes
npx aws-cdk@2 deploy BurnData  # deploy one stack (needs AWS credentials, us-east-1)
npx aws-cdk@2 deploy --all     # deploy everything
npx aws-cdk@2 destroy --all    # tear down
```
First time in a new account: `npx aws-cdk@2 bootstrap aws://<account-id>/us-east-1`.

To deploy, prefer `make deploy` and `make deploy-<Stack>` from the repo root. They keep people sign-in
and the hosted dashboard as this account runs them (see "Deploys follow the account" below). A bare
`npx aws-cdk@2 deploy` passes no flags, so it switches both off in BurnPeople and BurnApi.

Teardown note: Secrets Manager keeps deleted secrets for a recovery window, so redeploying right
after a destroy can fail on the secret names. Force-delete them first:
`aws secretsmanager delete-secret --secret-id burn-system/fingerprint-key --force-delete-without-recovery`
(same for `burn-system/demo-token`).

## The website
`burn_infra/site.py` serves the website in `site/` from a private S3 bucket through CloudFront, at the
distribution's own `https://<id>.cloudfront.net` address (no custom domain). `StaticSite` is the
reusable part: a name and a built folder in, a bucket and a distribution out.

```bash
make site-deploy   # npm ci + build in site/, deploy BurnSite, print the address
VITE_DASHBOARD_URL=https://... make site-deploy   # the same, with the site's dashboard link set
```
Without `VITE_DASHBOARD_URL`, the dashboard link points at the hosted dashboard once it serves a page
(see below), and stays unset before that.

- Only the distribution can read the bucket (origin access control). HTTP redirects to HTTPS.
- Every response carries HSTS, nosniff, `X-Frame-Options: DENY`, a strict referrer policy and a CSP that
  allows only the site's own files.
- `index.html` is sent with `Cache-Control: no-cache`. The hashed files under `assets/` are cached for a
  year. Each upload invalidates CloudFront's cache.
- The address is in SSM at `/burn/site/url` and in the stack output `Url`.
- Without a build (`site/dist/index.html` missing), synth and deploy still work: the stack creates the
  bucket and distribution, uploads nothing and leaves the files already there.
- The first deploy takes several minutes while CloudFront sets up the distribution.

## The hosted dashboard
`burn_infra/dashboard.py` serves the dashboard at the root of its own CloudFront distribution (a second
`StaticSite`), so the website's Sign in leads to a dashboard nobody has to run locally. The dashboard
signs in and out at its origin's root, which is why it is not a path under the website's distribution.

It goes live only once people sign-in is on: before that, a dashboard build can carry the admin demo
token, which must never be public.

- BurnDashboard never uploads `dashboard/dist` by itself. Only `make dashboard-deploy` uploads, by
  deploying with `-c burn:dashboard_build=checked` after its checks pass:
  - people sign-in is on;
  - the dashboard is rebuilt with the deployed API and sign-in values, local development off and an
    empty demo token;
  - no file in the build holds a demo token (from `.env`, `dashboard/.env*` or the deployed secret),
    or sets `x-burn-demo-token` to a value.

  Every other deploy (`make deploy`, `cdk deploy --all`) creates the bucket and distribution and leaves
  the uploaded files as they are.
- `-c burn:dashboard_hosted=on` (default off) adds the hosted dashboard's root to the people pool's
  callback and sign-out URLs, and its origin to the API's CORS. BurnPeople and BurnApi read the address
  from SSM (`/burn/dashboard/url`) when they deploy, and depend on BurnDashboard. With the flag off,
  neither stack changes.
- The CSP is the website's, plus the Burn API and the people sign-in domain in `connect-src`. Before
  hosting, those are wildcards for the region, so BurnDashboard depends on no other stack. With
  `burn:dashboard_hosted=on`, they are the exact origins from SSM (`/burn/api/url`, `/burn/people/domain`),
  read when BurnDashboard deploys.

Deploy order:
1. Switch people sign-in on: `make deploy-BurnApi PEOPLE_AUTH=on`, which deploys BurnPeople first.
2. `make dashboard-deploy`: refuses unless sign-in is on. It builds and checks the dashboard, uploads it
   and prints its address.
3. `make dashboard-hosted`: refuses unless the hosted dashboard serves a page. It deploys BurnDashboard
   (its CSP pinned; the uploaded files stay), BurnPeople and BurnApi with
   `-c burn:people_auth=on -c burn:dashboard_hosted=on`.
4. `make site-deploy`: the website's dashboard link now points at the hosted dashboard.

### Deploys follow the account
`make deploy` and `make deploy-<Stack>` pass `burn:people_auth` and `burn:dashboard_hosted` as this
account runs them. `burn_api/scripts/deploy_flags.py` reads that state:
- sign-in is on when SSM `/burn/people/enabled` is `on`, which BurnApi writes from its own flag;
- the dashboard is hosted when sign-in is on, `/burn/dashboard/url` exists, and the dashboard serves a
  page. An empty distribution answers 403, so it counts as not hosted.

So after the steps above, every later deploy keeps sign-in and the hosted dashboard on. Nothing is
committed to `cdk.json`, so a checkout deploying to another account starts with both off. When the
hosted dashboard doesn't answer at all, the deploy refuses rather than guess. To change either on
purpose, add `PEOPLE_AUTH=on|off` or `DASHBOARD_HOSTED=on|off`, e.g.
`make deploy-BurnApi PEOPLE_AUTH=off`.

## FAQ
- **Why so many stacks?** Each component deploys on its own, so changing one part never
  redeploys or risks another.
- **Where do the secrets come from?** AWS generates them at deploy time. No secret value is in the
  repo, in CDK code, or in a CloudFormation template.
- **Is anything wildcard?** No execution role of Burn's own Lambdas gets wildcard actions. Each gets only
  the table and secret-name actions it needs. The website stack also runs two helper Lambdas that come
  with CDK: one uploads the build, one empties the bucket on teardown. They get CDK's standard S3 grants
  (such as `s3:GetObject*`) on the website's bucket, and the upload one reads CDK's own asset bucket. The
  upload Lambda may also create CloudFront invalidations, which CDK grants on every distribution in the
  account.
- **Why is the website's bucket private when the site is public?** CloudFront is the only reader, so
  every visitor gets HTTPS, the security headers and the cache. Nobody can list or read the bucket
  directly.
- **Can the hosted dashboard leak the admin token?** Not through the deploy path. The dashboard is
  hosted only once people sign-in is on, and its build gets an empty token. The build is scanned for
  every known token value before upload, and BurnDashboard uploads nothing unless that check ran.
